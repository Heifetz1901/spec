# ADR 格式

ADR 存放于 `docs/adr/`，顺序编号：`0001-slug.md`、`0002-slug.md` 等。
`docs/adr/` 目录懒创建：仅在第一个 ADR 需要时创建。

## 模板

```
# {决策短标题}
{1-3 句：背景是什么、我们决定了什么、为什么。}
```

就这些。ADR 可以只有一段。价值在于记录*做过*这个决定和*为什么*，不在于填表格。

## 可选节

仅当真有价值才加，多数 ADR 用不上：

- **状态（Status）** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策会被重新审视时有用
- **备选方案（Considered Options）**：仅当被否的备选值得记住
- **后果（Consequences）**：仅当非显然的下游影响需要点明

## 编号

扫 `docs/adr/` 取现有最大号 +1。

## 何时提议 ADR

三条全真才写：

1. **难以逆转**：之后改主意的代价是实质性的
2. **缺上下文会费解**：未来读者看代码会问「他们到底为什么这么做？」
3. **真实权衡的结果**：确实存在备选，且你出于特定理由选了其一

容易逆转→跳过（改回来就是了）；不令人意外→没人会问为什么；没有真实备选→除了「我们做了显然的事」无可记录。

### 合格场景

- **架构形态**。「我们用 monorepo」「写模型事件溯源，读模型投影到 Postgres」
- **上下文间集成模式**。「Ordering 与 Billing 走领域事件而非同步 HTTP」
- **带锁定的技术选型**。数据库/消息总线/认证方/部署目标——不是每个库，只收换掉要花一个季度的
- **边界与归属决策**。「Customer 数据归 Customer 上下文所有，其他上下文仅按 ID 引用」——明确的「不」和「是」同样有价值
- **刻意偏离常规**。「我们手写 SQL 不用 ORM，因为 X」——任何合理读者会假设相反的地方；防止下个工程师把刻意为之的东西『修』回去
- **代码里看不见的约束**。「合规要求不能用 AWS」「因合作方 API 合同，响应必须低于 200ms」
- **不明显否决**。若考虑过 GraphQL 因细微理由选了 REST，记下来——否则六个月后有人会再提 GraphQL
