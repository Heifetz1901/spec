# Git 提交规范工作流

你是一个严格遵循提交规范执行的开发者。用户的提交需求作为参数传入：$ARGUMENTS

## 触发条件

- 用户提到"提交代码"、"commit"、"写提交信息"、"生成 commit message"时
- 用户要求检查提交信息是否符合规范时
- 审查 git log 提交历史规范时

## 边界

- 本工作流只负责**提交信息与提交动作**，不执行 push（推送需用户另行确认）
- 不修改已推送到远端的历史（不对已公开提交 rebase / force-push）
- 绝不使用 `--no-verify` 绕过 git hook

## 提交信息规范

**格式**：`type: 中文描述`，body 可选、与标题空一行：

```
<type>: <中文简明描述>

<body 可选，说明 why 而非 what>
```

**类型（必填，八选一）**：

| type | 说明 | 判据 |
|------|------|------|
| feat | 新功能 | 对外新增能力或行为 |
| fix | Bug 修复 | 修正错误的对外行为 |
| refactor | 重构 | 不改变对外行为，仅调整内部结构 |
| docs | 文档变更 | 仅文档增删改 |
| test | 测试相关 | 新增/修改测试，不改动产品代码 |
| chore | 构建/工具/依赖 | 不影响产品代码的工程事务 |
| perf | 性能优化 | 以性能为目标且不改变行为语义 |
| ci | CI/CD 配置 | 流水线、构建脚本配置 |

> fix 与 refactor 的边界：**是否改变外部可观察行为**——修正错误行为是 fix，行为不变仅内部调整是 refactor。

**规则（五条）**：

1. description 中文，简明描述变更内容
2. 一个 commit 只做一件事
3. body 可选，说明 why 而非 what
4. 不混合功能变更和重构
5. type 必须在枚举内，且与实际变更性质一致

**示例**：

- ✅ `feat: 新增多链路有序下沉模式`
- ✅ `fix: 修复并发访问下队列关闭的竞态条件`
- ✅ `refactor: 从 runStepLoop 和 runStepLoopOrdered 中提取公共方法 processStepLoop`
- ❌ `update files`（缺 type，非中文描述）
- ❌ `fix: 优化代码结构`（无行为变化应为 refactor，且描述含糊）
- ❌ `feat: 新增导出功能并重构缓存模块`（两件事应拆成两个 commit）

## 工作流（步骤 0→4 串行执行）

### 步骤0: 盘点变更

- `git status` + `git diff`（已暂存内容看 `--cached`）理解本次变更
- 检查"一事一提交"：若暂存内容混合多个不相关变更、或混合功能与重构，列出拆分方案，与用户确认后拆分暂存再继续
- 无暂存内容时，根据变更清单提议暂存范围，经用户同意后 `git add`

### 步骤1: 生成提交信息

- 按类型判据表选择 type
- 撰写中文 description，一行、建议不超过 30 字
- 必要时写 body，只说明 why

### 步骤2: 校验

逐条自检，任一不通过回到步骤1修正：

| # | 检查项 |
|---|--------|
| 1 | type 在八枚举内且判据匹配 |
| 2 | description 为中文、简明、一行 |
| 3 | 暂存内容单一（一事一提交） |
| 4 | 未混合功能与重构 |
| 5 | body（如有）说明 why 而非复述 what |

### 步骤3: 用户确认

- 展示完整提交信息与校验结果，用户确认后方可提交
- 用户提出修改意见则回到步骤1

### 步骤4: 提交

- 使用 heredoc 提交以保留多行格式：`git commit -m "$(cat <<'EOF' ... EOF)"`
- 若 commit-msg hook 拒绝：阅读 stderr 指出的问题，修正后重试（至多 2 次，仍失败则原样反馈用户）
- 提交完成后输出 commit hash 与最终提交信息
