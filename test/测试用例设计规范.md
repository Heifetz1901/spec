# 测试用例设计规范

## 1. 文档概述

### 1.1 目的

本规范定义测试用例设计的方法论、编写规范、评审标准及覆盖度要求，适用于所有项目的功能测试用例设计与评审。

### 1.2 适用范围

- 需求分析阶段的测试场景梳理
- 详细设计阶段的测试用例编写
- 测试执行阶段的用例维护与补充

### 1.3 术语定义

| 术语 | 定义 |
|------|------|
| 测试用例 | 为验证软件是否满足特定需求而设计的一组测试输入、执行条件和预期结果 |
| 等价类 | 输入域的子集，该子集中的任意输入都能揭示相同的缺陷 |
| 边界值 | 输入域边界及其附近的值，是缺陷高发区 |
| 判定表 | 描述多条件组合与对应动作关系的表格 |
| 正向用例 | 验证功能在正常输入下按预期工作的用例 |
| 逆向用例 | 验证功能在异常或非法输入下正确处理的用例 |

## 2. 用例编号规则

### 2.1 编号格式

```
TC-{模块代码}-{功能序号}-{用例序号}
```

- **模块代码**：2-4位大写字母，表示所属功能模块
- **功能序号**：2位数字，表示模块下的功能分类
- **用例序号**：3位数字，表示具体用例，按编写顺序递增

### 2.2 编号示例

```
TC-ORD-01-001    订单模块 - 创建订单功能 - 第1条用例
TC-PAY-02-015    支付模块 - 退款功能 - 第15条用例
TC-USR-03-002    用户模块 - 权限校验功能 - 第2条用例
```

### 2.3 编号管理

- 编号一旦分配不可复用，即使用例被删除也不可重新分配
- 用例拆分时，原编号保留，新增子用例追加后缀（如 TC-ORD-01-001-1）
- 不同模块的模块代码在项目启动时统一分配，避免冲突

## 3. 用例优先级

| 优先级 | 定义 | 覆盖要求 | 示例 |
|--------|------|---------|------|
| P0-冒烟 | 核心正向流程，阻断性功能，系统不可用的场景 | 100% | 主流程下单、核心支付路径 |
| P1-关键 | 主要业务场景，高频使用路径 | 100% | 常规参数组合、主要分支路径 |
| P2-一般 | 边界条件、异常路径、低频场景 | 80%+ | 边界值、异常输入、容错处理 |
| P3-边缘 | 极端场景、多条件组合、性能相关 | 按需 | 并发冲突、超大数据量、极端参数 |

## 4. 用例模板

### 4.1 用例列表

所有测试用例以列表形式集中展现，按模块分组，便于总览和检索。

```
## 用例列表

### {模块名称}（{模块代码}）

| 用例编号 | 用例名称 | 优先级 | 标签 | 前置条件 | 测试输入 | 操作步骤 | 预期结果 |
|---------|---------|--------|------|---------|---------|---------|---------|
| TC-{模块}-01-001 | ... | P0 | 等价类 正向 | ... | ... | ... | ... |
| TC-{模块}-01-002 | ... | P1 | 边界值 正向 | ... | ... | ... | ... |
| TC-{模块}-02-001 | ... | P2 | 场景法 逆向 | ... | ... | ... | ... |
```

**列表说明**：

- 按模块分组，每个模块一个子标题
- 模块内按功能序号排序（同一功能的用例连续排列）
- 用例编号唯一，新增用例追加到所属模块末尾
- 随项目迭代持续更新，废弃用例标记删除线而非删除

### 4.2 标准用例模板

```
用例编号:    TC-{模块}-{功能}-{序号}
用例名称:    {简明描述测试场景，采用"条件+动作+预期"结构}
优先级:      P0 / P1 / P2 / P3
标签:        [{设计方法}] [{正向/逆向}]
前置条件:    {测试环境、数据准备、系统状态要求}

测试输入:
  | 参数 | 值 | 说明 |
  |------|----|------|
  | param1 | value1 | ... |
  | param2 | value2 | ... |

操作步骤:
  1. {步骤描述，包含操作对象和动作}
  2. {步骤描述}
  3. ...

预期结果:
  - {断言点1：系统状态/数据变化}
  - {断言点2：返回结果/页面展示}
  - {断言点3：副作用/关联影响}
```

### 4.2 简化用例模板（适用于数据驱动场景）

当多条用例仅输入数据不同、操作步骤和预期结果结构相同时，使用表格形式：

```
用例编号:    TC-{模块}-{功能}-001~010
用例名称:    {统一描述}
优先级:      P1
标签:        [等价类]
前置条件:    {公共前置条件}

测试数据:
  | 用例编号 | 输入参数 | 预期结果 | 备注 |
  |---------|---------|---------|------|
  | -001 | value1 | result1 | 有效等价类A |
  | -002 | value2 | result2 | 有效等价类B |
  | -003 | value3 | result3 | 无效等价类 |
```

### 4.3 断言编写要求

每条用例的预期结果应满足以下要求：

| 要求 | 说明 | 正确示例 | 错误示例 |
|------|------|---------|---------|
| 可验证 | 结果必须可明确判断通过/失败 | 返回状态码200，body包含orderId | 系统正常处理 |
| 具体化 | 明确字段值、数量、状态 | 查询结果返回3条记录 | 查询有结果 |
| 完整性 | 覆盖所有可观察的变化 | 返回成功 + 数据库状态更新 + 日志记录 | 接口返回成功 |
| 无歧义 | 不使用模糊表述 | 金额精确到分，值为100.00 | 金额正确 |

## 5. 设计方法

### 5.1 等价类划分

**原理**：将输入域划分为若干等价类，同一等价类中的值对揭露缺陷的效果等价，从每个等价类中选取少量代表值即可达到较高覆盖率。

**步骤**：

1. 识别所有输入条件（参数、状态、配置）
2. 对每个输入条件划分有效等价类和无效等价类
3. 为每个等价类编号
4. 为每个等价类选取代表值设计用例

**示例**：

某系统用户注册，年龄输入范围为 18-60 岁。

| 输入条件 | 有效等价类 | 无效等价类 |
|---------|-----------|-----------|
| 年龄 | 18-60 之间的整数 | <18、>60、非整数、空值、非数字 |
| 手机号 | 11位数字，1开头 | 非11位、非数字、非1开头、空值 |

**用例覆盖**：

| 用例 | 年龄 | 手机号 | 覆盖等价类 | 预期 |
|------|------|--------|-----------|------|
| 1 | 25 | 13800138000 | 有效年龄+有效手机 | 注册成功 |
| 2 | 17 | 13800138000 | 无效年龄(下界外) | 提示年龄不合法 |
| 3 | 61 | 13800138000 | 无效年龄(上界外) | 提示年龄不合法 |
| 4 | 25 | 1380013800 | 无效手机(位数不足) | 提示手机号不合法 |
| 5 | 25 | abc | 无效手机(非数字) | 提示手机号不合法 |

### 5.2 边界值分析

**原理**：大量缺陷出现在输入/输出的边界上，针对边界及其附近设计用例。

**步骤**：

1. 识别所有输入/输出的边界
2. 选取边界值及邻近值
3. 考虑开/闭区间对边界归属的影响

**边界选取规则**：

对于范围 `[a, b]`：

```
测试值: a-1, a, a+1, ..., b-1, b, b+1
         略外  略内      略内  略外
```

对于有序集合 `{v1, v2, ..., vn}`：

```
测试值: v1(最小), vn(最大), v_mid(中间值)
```

**示例**：

某分页查询，每页条数范围为 1-100。

| 测试值 | 位置 | 预期 |
|--------|------|------|
| 0 | 下界外 | 参数错误 |
| 1 | 下界上 | 正常返回 |
| 2 | 下界内 | 正常返回 |
| 50 | 中间值 | 正常返回 |
| 99 | 上界内 | 正常返回 |
| 100 | 上界上 | 正常返回 |
| 101 | 上界外 | 参数错误 |

### 5.3 判定表（决策表）

**原理**：当多个条件的组合决定不同处理结果时，使用判定表穷举所有组合，确保每种组合都有对应用例。

**步骤**：

1. 列出所有条件（输入参数、状态标志）
2. 列出所有可能的动作（处理结果、输出）
3. 填写每种条件组合对应的动作
4. 合并等价行（某些条件组合产生相同结果时）
5. 每行生成一条用例

**示例**：

某折扣规则：会员等级(VIP/普通) × 促销活动(有/无) × 商品类型(自营/第三方)。

| # | 会员等级 | 促销活动 | 商品类型 | 折扣规则 |
|---|---------|---------|---------|---------|
| 1 | VIP | 有 | 自营 | 8折 + 促销折扣 |
| 2 | VIP | 有 | 第三方 | 9折 + 促销折扣 |
| 3 | VIP | 无 | 自营 | 8折 |
| 4 | VIP | 无 | 第三方 | 9折 |
| 5 | 普通 | 有 | 自营 | 促销折扣 |
| 6 | 普通 | 有 | 第三方 | 促销折扣 |
| 7 | 普通 | 无 | 自营 | 无折扣 |
| 8 | 普通 | 无 | 第三方 | 无折扣 |

> 注：5和6结果相同，可合并为一条用例，但建议分开以便独立验证。

### 5.4 场景法

**原理**：按照业务流程的路径设计用例，覆盖正常流（Happy Path）和各种异常流（Alternative Path）。

**步骤**：

1. 梳理业务流程图（正常流）
2. 识别每个环节可能的异常/分支（异常流）
3. 从起点到终点组合不同的路径
4. 每条完整路径生成一条用例

**示例**：

电商下单流程：

```
正常流: 登录 → 选商品 → 加入购物车 → 提交订单 → 支付 → 发货 → 确认收货
异常流A: 登录 → 选商品 → 加入购物车 → 提交订单 → 支付失败 → 重新支付 → 成功
异常流B: 登录 → 选商品 → 加入购物车 → 提交订单 → 支付 → 超时未发货 → 自动退款
异常流C: 登录 → 选商品(已下架) → 提示已下架
异常流D: 登录 → 选商品 → 加入购物车 → 提交订单(库存不足) → 提示库存不足
```

### 5.5 方法选择指南

| 场景特征 | 推荐方法 | 说明 |
|---------|---------|------|
| 单一输入，离散取值 | 等价类划分 | 如枚举类型、下拉选项 |
| 单一输入，连续数值范围 | 边界值分析 | 如金额、数量、日期范围 |
| 多个条件组合决定结果 | 判定表 | 如费率计算、权限判断、折扣规则 |
| 有明确业务流程 | 场景法 | 如订单流程、审批流程、状态机 |
| 流程中含条件分支 | 场景法 + 判定表 | 先梳理流程路径，再对分支点使用判定表 |
| 流程中含数值计算 | 场景法 + 边界值 | 先梳理流程路径，再对计算输入使用边界值 |

## 6. 用例设计维度

### 6.1 功能维度

| 维度 | 关注点 | 适用方法 |
|------|--------|---------|
| 正向功能 | 正常输入下的正确行为 | 等价类、场景法 |
| 参数校验 | 非法参数、缺失参数、类型错误 | 等价类（无效类） |
| 边界条件 | 数值边界、长度边界、时间边界 | 边界值分析 |
| 条件组合 | 多条件交叉影响 | 判定表 |
| 业务流程 | 端到端流程正确性 | 场景法 |
| 异常处理 | 异常输入的容错和提示 | 等价类 + 场景法 |

### 6.2 非功能维度

| 维度 | 关注点 | 用例设计要点 |
|------|--------|-------------|
| 性能 | 响应时间、吞吐量、资源占用 | 大数据量输入、高并发场景 |
| 安全 | 权限控制、数据保护、注入攻击 | 越权访问、SQL注入、XSS、敏感数据暴露 |
| 兼容性 | 多环境、多版本 | 不同浏览器、操作系统、接口版本 |
| 可靠性 | 容错、恢复、幂等 | 网络中断、重复提交、超时重试 |
| 数据一致性 | 并发、分布式场景 | 并发修改、分布式事务、数据同步 |

## 7. 用例评审标准

### 7.1 评审检查项

每条用例提交评审前，作者应自检以下项目：

| # | 检查项 | 通过标准 |
|---|--------|---------|
| 1 | 编号规范 | 符合编号规则，无重复、无遗漏 |
| 2 | 名称清晰 | 仅看名称即可理解测试场景 |
| 3 | 优先级合理 | 与场景重要性匹配 |
| 4 | 前置条件完整 | 包含所有必要的环境和数据准备 |
| 5 | 输入数据具体 | 所有参数有明确取值，无模糊描述 |
| 6 | 步骤可执行 | 按步骤可完整复现，无遗漏步骤 |
| 7 | 预期结果可验证 | 每个断言点可明确判断通过/失败 |
| 8 | 方法匹配 | 使用的设计方法适合该场景 |
| 9 | 无冗余 | 与已有用例不重复 |

### 7.2 评审流程

```
作者自检 → 同行评审 → 测试负责人审核 → 定稿
```

- **同行评审**：由另一名测试人员检查用例质量和覆盖度
- **负责人审核**：确认整体覆盖度满足要求，优先级分配合理

## 8. 覆盖度跟踪

### 8.1 覆盖度定义

| 覆盖类型 | 计算方式 | 目标 |
|---------|---------|------|
| 需求覆盖率 | 已覆盖需求数 / 总需求数 × 100% | ≥ 100%（每条需求至少一条用例） |
| 等价类覆盖率 | 已覆盖等价类 / 总等价类 × 100% | ≥ 95% |
| 判定表覆盖率 | 已覆盖规则行 / 总规则行 × 100% | 100% |
| 场景覆盖率 | 已覆盖路径 / 总路径 × 100% | 正常流100%，异常流≥80% |

### 8.2 覆盖度检查清单

用例编写完成后，按以下维度检查覆盖完整性：

- [ ] 每条功能需求至少对应一条正向用例
- [ ] 每个输入参数的有效/无效等价类均已覆盖
- [ ] 每个数值型参数的边界值均已测试
- [ ] 判定表中每种条件组合均有对应用例
- [ ] 业务流程的正常流和主要异常流均已覆盖
- [ ] 异常输入（空值、超长、特殊字符、非法类型）均已测试
- [ ] 多条件组合的关键场景已通过判定表覆盖
- [ ] 并发、幂等、超时等非功能场景已按需覆盖

## 9. 用例维护规范

### 9.1 变更管理

| 变更类型 | 处理方式 |
|---------|---------|
| 需求变更 | 标记受影响用例 → 更新用例 → 评审 |
| 缺陷修复补充 | 新增回归用例 → 关联缺陷编号 |
| 用例失效 | 标记为废弃（不删除，保留历史） → 说明废弃原因 |
| 用例优化 | 修订后标注修改日期和修改人 |

### 9.2 版本管理

- 用例文档随项目版本一起归档
- 每轮测试后记录用例通过率
- 用例库定期清理废弃用例（每季度）

## 附录A：常见测试场景 checklist

### A.1 输入校验

| 场景 | 测试点 |
|------|--------|
| 必填字段 | 空值、空白字符、仅空格 |
| 数值范围 | 超下限、超上限、负数、零、极大值 |
| 字符串长度 | 空串、最小长度、最大长度、超长 |
| 格式校验 | 邮箱、手机号、身份证、日期格式 |
| 特殊字符 | SQL关键字、HTML标签、引号、反斜杠 |
| 类型校验 | 数字字段传字符串、字符串字段传数字 |

### A.2 接口测试

| 场景 | 测试点 |
|------|--------|
| 参数完整性 | 缺少必选参数、多传参数、参数名错误 |
| 参数类型 | 类型不匹配、null值、空数组 |
| 业务逻辑 | 正常流程、边界条件、异常分支 |
| 返回值 | 正确返回结构、错误码覆盖、分页边界 |
| 幂等性 | 重复请求、并发请求 |

### A.3 状态转换

| 场景 | 测试点 |
|------|--------|
| 正向转换 | 按顺序逐步转换 |
| 跳步转换 | 跳过中间状态直接到目标状态 |
| 逆向转换 | 回退到前一状态 |
| 非法转换 | 不允许的状态转换 |
| 并发转换 | 同一对象同时触发状态变更 |

### A.4 数据处理

| 场景 | 测试点 |
|------|--------|
| 查询 | 精确匹配、模糊匹配、范围查询、排序、分页 |
| 新增 | 唯一性冲突、关联数据不存在 |
| 修改 | 并发修改、部分更新、不可修改字段 |
| 删除 | 有关联数据、批量删除、重复删除 |
