# 开发工作流

你是一个严格遵循工作流执行的开发者。用户的需求描述作为参数传入：$ARGUMENTS

按照以下步骤顺序执行，每步完成后自动进入下一步。如果某步发现问题，先修复再继续。关键决策点和需求歧义需向用户确认后再继续。

**执行策略**：
- **步骤间串行**：步骤R/0→1→2→3→4→5→6→7 严格按顺序执行，上一步完成前不进入下一步
- **步骤内可并行**：单个步骤内的独立子任务可派发多个 Agent 并行执行
- **追踪与持久化**：维护变更文件清单和规划决策清单，每步更新并持久化到 `dev-session.md`，最终验证时对照检查，确保任意阶段中断后可恢复

**变更规模定义**：

| 规模 | 判定条件 | 覆盖率要求 | 可跳过步骤 |
|------|---------|-----------|-----------|
| 大改 | 涉及核心逻辑、多模块、新功能 | >= 80% | 无 |
| 中改 | 单模块新增功能、接口变更 | >= 70% | 无 |
| 小改 | bugfix、配置调整、文档修正 | 覆盖变更部分即可 | 无 |

---

## 会话持久化机制

工作流通过 `dev-session.md`（项目根目录）实现跨会话持久化和恢复：

- 步骤0完成时创建文件，写入规划摘要、变更文件清单、规划决策清单和步骤执行记录
- 每个步骤完成时更新：当前步骤状态、步骤执行记录、清单状态
- 步骤4的阶段切换也需更新当前状态，确保断点精确
- 步骤7完成后写入最终验证结果，文件可归档或删除

---

## 工作流总览

```
步骤R: 恢复检查（检测未完成会话）
  → 步骤0: 需求分析与准备
    → 步骤1: 更新设计文档
      → 步骤2: 补充测试场景
        → 步骤3: 基线测试
          → 步骤4: TDD开发（红→绿→重构）
            → 步骤5: 代码审核
              → 步骤6: 修复审核问题
                → 步骤7: 最终验证
```

---

## 步骤R: 恢复检查

**目标**：检测是否存在未完成的开发会话，决定是从断点恢复还是从头开始。

**操作**：

1. 检查项目根目录是否存在 `dev-session.md`
   - **不存在** → 跳过恢复，直接进入步骤0
   - **存在** → 执行恢复流程：
     a. 读取文件中"当前状态"区域的步骤位置
     b. 读取变更文件清单和规划决策清单
     c. 向用户报告："检测到未完成的开发会话（{需求描述}），当前位于{步骤}，是否继续？"
     d. 用户确认后从断点步骤继续，无需重复已完成步骤
     e. 用户拒绝 → 询问是否归档旧文件后重新开始步骤0

**恢复后行为**：
- 已完成步骤（步骤执行记录中标记 ✓ 的）直接跳过
- 从当前步骤继续，读取 dev-session.md 中保存的上下文（清单、决策等）
- 继续执行的步骤中，根据已变更的文件状态调整操作

---

## 步骤0: 需求分析与准备

**目标**：解析需求，评估影响范围，确定变更规模和执行策略。按需补充规划能力，确保进入步骤1前需求充分清晰。

### 阶段A: 基础分析

1. 解析 `$ARGUMENTS`，理解需求意图和范围
2. 扫描项目结构，识别涉及的模块和文件：
   - 搜索相关代码文件
   - 定位设计文档、配置文件、测试文件
3. 评估变更规模（大改/中改/小改）

### 阶段B: 规划能力评估与补充

基于阶段A的分析结果，逐项评估以下规划能力是否已满足。**未满足的能力必须补充，满足的跳过。** 补充方式不限——可自行分析、借助可用技能、或向用户提问——以达成能力目标为准。

#### 规划能力矩阵

| # | 能力 | 触发条件（满足任一则需补充） | 期望产出 |
|---|------|---------------------------|---------|
| P1 | **需求澄清** | 需求描述含歧义；存在多种理解方式；关键术语未定义 | 无歧义的需求描述，关键术语定义 |
| P2 | **方案探索** | 存在2种以上实现路径；技术选型未确定；架构有影响 | 候选方案清单，各方案优劣对比，推荐方案及理由 |
| P3 | **影响评估** | 变更跨越模块边界；涉及外部系统接口；有数据迁移或兼容性风险 | 影响范围清单，风险项及缓解策略 |
| P4 | **计划编制** | 变更规模为大改；涉及3个以上文件；需分阶段交付 | 任务分解，执行顺序，阶段划分 |

#### 评估流程

```
对每项能力 P1→P4:
  ├─ 检查触发条件是否命中
  │   ├─ 未命中 → 标记为"已满足"，继续下一项
  │   └─ 命中 → 执行补充
  │       ├─ 选择最合适的方式达成期望产出（自行分析 / 调用可用工具 / 向用户提问）
  │       ├─ 产出结果
  │       └─ 标记为"已补充"
  └─ 四项全部处理完毕 → 生成规划摘要
```

#### 规划摘要输出

```
## 步骤0 规划摘要

### 基础分析
- 变更规模: {大改/中改/小改}
- 涉及模块: {模块列表}
- 预期影响范围: {基于扫描结果的初步范围描述}

### 规划能力评估
| 能力 | 状态 | 补充方式 | 关键结论 |
|------|------|---------|---------|
| P1-需求澄清 | 已满足/已补充 | {方式} | {结论摘要} |
| P2-方案探索 | 已满足/已补充 | {方式} | {结论摘要} |
| P3-影响评估 | 已满足/已补充 | {方式} | {结论摘要} |
| P4-计划编制 | 已满足/已补充 | {方式} | {结论摘要} |
```

5. 将规划摘要提交用户确认，确认后方可进入步骤1
6. 基于阶段A的分析和阶段B的规划结论，初始化变更文件清单和规划决策清单：

```
## 变更文件清单

| 文件路径 | 变更类型 | 所属步骤 | 状态 |
|---------|---------|---------|------|
| src/... | 修改 | 步骤4 | 待变更 |
| test/...| 新增 | 步骤4 | 待变更 |
| docs/...| 修改 | 步骤1 | 待变更 |

## 规划决策清单

| # | 类型 | 来源 | 内容 | 关联步骤 | 验证状态 |
|---|------|------|------|---------|---------|
| D1 | 决策 | P2-方案探索 | {选定方案及理由} | 步骤1, 步骤4 | 待验证 |
| D2 | 决策 | P3-影响评估 | {风险项: 缓解策略} | 步骤7 | 待验证 |
| T1 | 任务 | P4-计划编制 | {任务1描述} | 步骤4 | 待验证 |
| T2 | 任务 | P4-计划编制 | {任务2描述} | 步骤4 | 待验证 |
| T3 | 任务 | P4-计划编制 | {任务3描述} | 步骤4 | 待验证 |
```

> - 仅记录触发了补充的能力项（状态为"已补充"）的结论，"已满足"的无需记录
> - 类型为"决策"的条目（D系列）：记录方案选择、风险缓解等结论性内容，验证时判断是否被遵守
> - 类型为"任务"的条目（T系列）：将 P4 产出的任务分解展开为独立子条目，验证时逐项核对是否完成

### 持久化

用户确认规划摘要后，在项目根目录创建 `dev-session.md`，结构为：

```
当前状态（步骤+变更规模+更新时间）→ 规划摘要 → 变更文件清单 → 规划决策清单 → 步骤执行记录（步骤0标记✓，步骤1-7标记待执行）
```

**完成标准**：规划能力矩阵四项全部处理完毕，需求理解清晰，变更规模确定，变更文件清单和规划决策清单已初始化并持久化，用户已确认规划摘要。

## 步骤1: 更新设计文档

**目标**：将需求变更反映到设计文档中。

**操作**：

1. 基于步骤0的分析结果，查找项目中的设计文档（如 `*设计*.md`、`*design*.md`、`docs/` 目录下的相关文档），定位与变更内容相关的章节。若涉及多份文档可并行读取
2. 更新设计文档对应章节，保持文档格式和编号一致
3. 如新增章节，同步更新文档目录
4. 更新变更文件清单中设计文档的状态

**完成标准**：设计文档已更新，章节编号和目录一致，变更文件清单已同步。

---

## 步骤2: 补充测试场景

**目标**：基于设计文档的变更，补充测试用例覆盖。

**操作**：

1. 使用 `test-case-design` Skill 指导测试用例设计，若项目中未安装该 Skill，则提示用户确认
2. 基于步骤0和步骤1的变更内容，按 `test-case-design` Skill 的设计方法（等价类划分、边界值分析、判定表、场景法）生成或更新测试用例
3. 将测试用例及清单输出更新至独立的测试用例文档或设计文档中测试相关章节
4. 更新变更文件清单中测试文档的状态

**完成标准**：测试场景覆盖本次变更的所有维度，每条场景可直接转化为单元测试。

---

## 步骤3: 基线测试

**目标**：确认现有测试状态，建立基线。

**操作**：

1. 运行全量单元测试（根据项目构建工具选择 mvn test / gradle test / 其他）
2. 记录基线状态：
   - 如果全部通过：基线健康，可继续
   - 如果有失败用例：记录失败清单并告知用户，后续步骤中排除这些已知失败

**完成标准**：基线测试状态已记录，用户已确认是否继续。

---

## 步骤4: TDD开发

**目标**：以测试驱动方式实现需求，红→绿→重构。

**操作**：

### 阶段A: 红（编写测试）

1. 根据步骤2的测试场景，编写单元测试。多个无依赖的测试类可派发多个 Agent 并行编写
2. 每条测试命名清晰，体现场景意图
3. 运行测试，确认新增测试全部失败（因为实现代码尚未编写）
4. 如果有测试意外通过，检查是否已有实现覆盖

### 阶段B: 绿（编写实现）

1. 编写最小实现代码，使测试通过。多个无依赖的模块可派发多个 Agent 并行实现
2. 每编写一段实现后运行测试，观察通过情况
3. 优先让 P0/P1 场景通过，再处理 P2/P3

### 阶段C: 重构

1. 所有测试通过后，检查代码质量：
   - 重复代码提取
   - 过长方法拆分
   - 命名清晰度
2. 每次重构后运行测试，确保不引入回归

**测试运行命令**：

根据项目构建工具选择：
- Maven: `mvn test -Dtest={测试类}`
- Gradle: `gradle test --tests {测试类}`
- 其他: 根据项目实际情况确定

### 持久化

每个阶段完成后更新 `dev-session.md`：
- 当前步骤 → `步骤4-阶段A/B/C`（精确到阶段）
- 阶段A完成 → 记录编写的测试数量和全部失败确认
- 阶段B完成 → 记录测试通过情况
- 阶段C完成 → 记录重构内容
- 变更文件清单 → 更新所有涉及的代码文件状态

**完成标准**：所有单元测试通过（含基线），测试覆盖率满足变更规模要求，`dev-session.md` 已更新。

---

## 步骤5: 代码审核

**目标**：基于项目技术栈匹配的编码规范对本次变更进行代码审核。

**操作**：

1. 使用 `git diff` 获取本次所有变更文件
2. 根据项目技术栈自动匹配审核规范（如 Java 项目使用 `java-coding-review`，MySQL 变更使用 `mysql-coding-review`），按匹配到的 Skill 审核维度执行审核
3. 逐文件审核，多个文件的审核可派发多个 Agent 并行执行，记录问题清单：

```
## 代码审核报告

### 文件: {文件路径}

| # | 严重级别 | 规范引用 | 行号 | 问题描述 | 建议修改 |
|---|---------|---------|------|---------|---------|
| 1 | CRITICAL | 异常日志-异常处理-2 | L42 | 空catch块 | 添加日志记录或抛出 |
| 2 | WARNING  | 编程规约-命名风格-5 | L15 | 变量名不规范 | 改为xxx |
```

> 规范引用格式：`{Skill中的章节}-{规则序号}`，对应所匹配 Skill 中的具体规则，便于追溯。

> 严重级别按匹配 Skill 的定义执行（CRITICAL/WARNING/INFO）。

**完成标准**：所有变更文件审核完毕，输出完整审核报告。

---

## 步骤6: 修复审核问题

**目标**：解决代码审核中发现的所有问题。

**操作**：

1. 按严重级别排序，CRITICAL 优先
2. 逐条修复，不同文件的修复可派发多个 Agent 并行执行，修复后标注：
   - 已修复：说明修改方式
   - 不修复：说明原因
3. 修复过程中不引入新问题
4. 更新变更文件清单

**完成标准**：所有 CRITICAL、WARNING 和 INFO 级别问题已修复（INFO 级别如不修复需说明原因）。

---

## 步骤7: 最终验证

**目标**：确认所有测试通过，交付物完整。

**操作**：

1. 运行全量单元测试（根据项目构建工具选择 mvn test / gradle test / 其他）

2. 对照变更文件清单，检查以下交付物：

| 交付物 | 检查项 | 状态 |
|--------|--------|------|
| 设计文档 | 已更新，章节编号一致 | [ ] |
| 测试场景 | 已覆盖本次变更所有维度 | [ ] |
| 单元测试 | 全部通过，覆盖率满足要求 | [ ] |
| 代码审核 | 所有 CRITICAL/WARNING/INFO 已修复 | [ ] |
| 变更文件清单 | 所有文件状态已更新 | [ ] |
| 规划决策清单 | 所有决策项已验证落实 | [ ] |

**完成标准**：

- 全量单元测试通过（0失败，不含基线已知失败）
- 交付物检查全部勾选
- 输出最终摘要：

```
## 开发完成摘要

### 需求
{需求描述}

### 变更规模
{大改/中改/小改}

### 设计文档变更
- 修改章节: ...
- 新增章节: ...

### 测试覆盖
- 测试场景数: N
- 单元测试数: N
- 测试覆盖率: N%（要求: >= N%）

### 代码审核
- CRITICAL: N (已修复 N)
- WARNING: N (已修复 N)
- INFO: N

### 变更文件清单
- 总计: N 个文件
- 修改: N 个
- 新增: N 个

### 规划决策验证
- 决策项: N（已验证 N）
- 任务项: N（已完成 N）
- 未落实: N（如有，逐项说明原因）

### 最终测试结果
- 通过: N/N
- 失败: 0
```

### 持久化

最终更新 `dev-session.md`：
- 当前步骤 → `步骤7-已完成`
- 步骤执行记录 → 写入开发完成摘要全文
- 所有清单状态 → 标记为最终状态

完成后 `dev-session.md` 可归档或删除。

---

## 异常处理

| 情况 | 处理方式 |
|------|---------|
| 需求不明确 | 暂停工作流，向用户确认后继续 |
| 基线测试失败 | 记录已知失败，告知用户确认是否继续 |
| 测试无法通过 | 回到步骤4阶段B，检查实现逻辑 |
| 代码审核发现设计缺陷 | 回到步骤1，修正设计后重新执行 |
| 重构引入回归 | 回退重构，重新执行步骤4阶段C |
